1. OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

NexaCore operates a multi-cloud infrastructure strategy spanning AWS (primary), Azure (secondary, primarily for Microsoft workloads and healthcare clients), and limited GCP usage (ML/AI workloads). Our infrastructure serves both internal NexaCore operations and managed cloud environments for clients.

This document provides architectural reference for engineering, DevOps, and client solutions teams.

2. AWS INFRASTRUCTURE OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

2.1 Regions
- Primary: us-east-1 (N. Virginia) — All production workloads
- Secondary DR: us-west-2 (Oregon) — Disaster recovery, failover
- International: ap-south-1 (Mumbai) — Bangalore office operations and APAC client workloads

2.2 Core Services Used
- Compute: EC2, ECS (Fargate), Lambda
- Containers: EKS (Kubernetes — primary container platform)
- Storage: S3, EFS, EBS
- Database: RDS (PostgreSQL, MySQL), DynamoDB, ElastiCache (Redis)
- Networking: VPC, Transit Gateway, Route 53, CloudFront, ALB/NLB
- Security: IAM, GuardDuty, Security Hub, AWS Config, CloudTrail, KMS
- Monitoring: CloudWatch, integrated with Datadog
- CI/CD: GitHub Actions (primary), CodePipeline (legacy, being phased out)

2.3 Account Structure
NexaCore uses AWS Organizations with a multi-account architecture:
- Master/Management Account: Billing, SCPs, account management
- Shared Services Account: CI/CD tools, logging, monitoring
- Production Account: Live workloads
- Staging Account: Pre-production
- Development Account: Developer sandboxes
- Client Accounts: Dedicated AWS accounts for enterprise clients (isolated billing and governance)

Service Control Policies (SCPs) restrict certain actions across all accounts (e.g., disabling CloudTrail, disabling GuardDuty, creating unencrypted S3 buckets).

3.1 Use Cases
- Microsoft 365 and Azure AD (Entra ID) for identity and collaboration
- Healthcare client workloads (HIPAA-compliant Azure configurations)
- Some clients prefer Azure due to existing enterprise agreements

3.2 Key Services
- Identity: Azure Active Directory (SSO for all M365 and Azure services)
- Compute: Azure Kubernetes Service (AKS) for healthcare clients
- Storage: Azure Blob Storage, Azure SQL Database
- Security: Microsoft Defender for Cloud, Azure Sentinel (SIEM)
- Networking: Azure Virtual Network, Application Gateway

Several clients run hybrid environments (on-premises + Azure). NexaCore uses Azure ExpressRoute and site-to-site VPNs for these scenarios. [DRAFT — full connectivity diagram pending from network team]

4. CONTAINER AND KUBERNETES STRATEGY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

4.1 EKS as Primary Platform
All new microservices are deployed on Amazon EKS. NexaCore runs two EKS clusters:
- nexacore-prod: Production workloads (multi-AZ, auto-scaling enabled)
- nexacore-staging: Staging and pre-prod testing

4.2 Cluster Configuration
- Kubernetes version: 1.28 (as of Jan 2024; upgrade schedule: every 3 months)
- Node groups: Managed node groups using EC2 (m5.xlarge standard, c5.2xlarge for compute-intensive workloads)
- Cluster Autoscaler: Enabled; minimum 3 nodes, maximum 20 nodes per node group
- Ingress: NGINX Ingress Controller with AWS ALB integration

4.3 Service Mesh
[DRAFT] NexaCore is evaluating Istio vs AWS App Mesh for service mesh capabilities. Pilot running in staging environment. Decision expected Q2 2024. No service mesh currently in production.

4.4 Container Registry
Amazon ECR (Elastic Container Registry) is used for all Docker images. Images are scanned for vulnerabilities on push via ECR Enhanced Scanning (powered by Inspector). Images with Critical vulnerabilities are blocked from deployment by CI/CD pipeline policy.

5. NETWORKING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

5.1 VPC Design
Each AWS account uses a standard VPC template:
- CIDR: /16 address space (unique per account to avoid overlap)
- Subnets: Public (ALB/NAT), Private App (compute), Private Data (databases)
- NAT Gateway: Per AZ (3 AZs per region) for high availability
- VPC Flow Logs: Enabled and shipped to centralized S3/CloudWatch

5.2 DNS
Route 53 is used for internal and external DNS. Private hosted zones resolve internal service names. Public zones manage client-facing and corporate domains.

5.3 CDN
CloudFront is used for:
- Static asset distribution (web frontends)
- API caching (select client APIs)
- WAF integration (AWS WAF attached to all CloudFront distributions)

6. DISASTER RECOVERY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

6.1 Objectives
- RTO (Recovery Time Objective): 4 hours for Tier 1 services, 24 hours for Tier 2
- RPO (Recovery Point Objective): 1 hour for Tier 1, 24 hours for Tier 2

[DRAFT] The RTO/RPO targets for specific client services are being reviewed and may differ from internal targets. Client-specific DRPs (Disaster Recovery Plans) are maintained separately in the client folder in Confluence.

6.2 Backup Strategy
- RDS: Automated daily snapshots + point-in-time recovery (7-day retention for dev, 30-day for prod)
- S3: Versioning enabled + cross-region replication to us-west-2
- EBS: Daily snapshots via AWS Backup

6.3 DR Testing
Disaster recovery drills are conducted bi-annually (June and December). Results are documented and reviewed by the Engineering and Security teams. Last DR drill: June 2023. Issues found: cross-region failover for two legacy services exceeded RTO — remediation in progress.

7. COST MANAGEMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

- AWS Cost Explorer and Budgets are configured for all accounts
- Monthly budget alerts at 80% and 100% of planned spend
- Reserved Instances and Savings Plans cover ~60% of baseline EC2/RDS usage
- Tagging policy: all resources must be tagged with: Environment, Team, CostCenter, Project
- Untagged resources are flagged weekly by a Lambda function and owners are notified
